# 上传哈希与预览缓存隔离

日期：2026-10-23。实施与本地验证已完成；合并与 CI 结果以本次 PR 为准，公司环境未迁移或部署。

## 已确认的问题

上传完成只比较 init / complete 两次申报，没有计算实际源字节的 SHA-256。全局预览缓存按申报哈希、管线版本和通道命中，读取另一版本的 ready 行时直接签出产物；未就绪时，错误源版本可把共享缓存置为 failed。SVG worker 的源哈希校验发生在缓存命中之后，不能保护读取侧。

ONLYOFFICE 配置原来直接使用版本 contentHash 作为 document.key。官方规定同 key 会使用既有缓存，并要求不同服务与文档保持唯一性；实际跨文档显示效果尚未做 DocServer 端到端复现。[官方 document.key 定义](https://api.onlyoffice.com/docs/docs-api/usage-api/config/document/#key)

## 修复边界与取舍

- 上传完成通过对象存储流计算完整 SHA-256、核对实际读取长度，只保留 64 KiB 文件头；MIME 校验与哈希通过后才复制、写版本和投任务。入库、对象键与 CAD 后台登记均使用实际计算结果，沿用 `FILE_HASH_MISMATCH`（422）。
- 预览缓存唯一键改为 `version_id + pipeline_version + target`，读取额外绑定该版本的 contentHash。任务去重与对象键同步按版本隔离：`preview.job:version:{versionId}:{hash}:{pipeline}:{target}`、`previews/versions/{versionId}/{hash}/{pipeline}/{target}`。
- ready / failed 仅由 not_ready 转入，过期失败任务不能把 ready 降级。彻底删除只清本版本产物，移除按哈希反查和归属转移。
- ONLYOFFICE key 使用带用途前缀的 SHA-256，输入为服务实例地址、项目、文件、版本和内容哈希；符合官方长度 / 字符要求，同版本保持稳定，不同版本不共用 key。

仅校验新上传，无法处理已有版本里不可信的哈希；维持全局缓存还需要新增哈希验证来源及历史回填机制。本次选择版本隔离，完整关闭历史记录的跨文档读取与失败污染入口。代价是不同文件或版本即使字节相同也独立转换和保存预览；同一版本仍复用缓存。附件域的同项目文件复用、原文件下载和 CAD 的既有版本隔离不变。

完成上传新增一次完整的内网对象流读取与 SHA-256 计算，内存不随文件大小累积；接近上传上限的大文件耗时尚未实测，不将小夹具测试当作容量结论。

## 迁移与部署

追加迁移 `0067_preview_version_isolation.sql`：只失效旧预览缓存登记并修改唯一约束；源对象、文件、版本、审计与 outbox 历史不删除。旧登记曾可按未经验证的哈希转移归属，不能直接继承为可信版本缓存。

部署须停止旧 API / worker，执行迁移后启动同版本服务，避免新旧缓存规则混跑。首次预览按需重新生成；旧 outbox 历史不阻塞新的版本任务去重键。旧 `previews/{hash}/...` 私有对象不再签出，可在旧签名过期后独立清理；不得误删新的 `previews/versions/`。本次未执行公司环境迁移、对象清理或部署。

## 验证方式

- 修复前，5 个回归断言复现申报哈希被接受、另一版本 ready / failed 被继承以及不同 Office 文档同 key。
- 文件服务、预览读面、转换队列、受控读取与 S3 适配的定向回归；另有实际流截断、超长、流中断和全流 SHA-256 测试。
- 真实 PostgreSQL 集成用例验证旧缓存失效、源版本 / 审计保留、同哈希多版本并存、失败隔离和 ready 状态保护。运行需设置仅供测试的 `PREVIEW_TEST_DATABASE_URL`，执行 `test/preview-isolation.integration.test.ts`。
- 原 LibreOffice / 全局哈希缓存时代的 `m4-preview*` 回放属于历史工具，不作为当前 SVG 管道的验收依据。当前浏览器入口为 `frontend/scripts/h1-svg-preview-e2e.mjs`。

验证数量和发布状态以本次实际交付记录为准，不将配置 key 的回归测试表述为 DocServer 端到端攻击验证。

本次实测：7 个定向测试文件、225 项全部通过；真实 PostgreSQL 18.6 中完整执行至 `0067`（共 66 个迁移），重复执行无漂移；Drizzle 检查通过（59 表、625 列、194 索引 / 唯一约束、225 CHECK）。前端 typecheck / build、服务端 typecheck / build / 边界检查及契约生成漂移检查通过。未执行 DocServer 真实串读端到端、大文件容量或公司环境部署验证。
