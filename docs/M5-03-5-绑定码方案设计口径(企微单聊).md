## 1. 背景与硬约束

- 企微智能机器人回调的 `from.userid`：**若机器人创建者不是企业超级管理员，则为企业主体下的加密 userid（open_userid）**（官方「接收消息 / 接收事件」原文；本仓实测见 §2）。
- 本项目**无法取得企微后台管理员权限**，因此两条替代路走不通：
  - 把机器人创建者改为企业超级管理员（回调即给明文 userid）；
  - 用自建应用调 `POST /cgi-bin/batch/openuserid_to_userid` 做密文 → 明文归一（需自建应用 access_token + 成员在该应用可见范围内）。
- 故 **明文 userid ↔ 密文 open_userid 的映射只能由用户侧交互产生**——这是本方案要解决的唯一问题。
- 产品口径（已定）：接受「每个用户对每个机器人先激活一次」的成本；**未激活推送不再是目标**。

## 3. 目标形态

**绑定（一次性 · 用户驱动）**
1. 用户在系统内请求绑定 → 服务端生成**绑定码**（6 位数字、TTL 5 分钟、一次性、与登录态 `user_id` 绑定）；
2. 用户在与机器人的**单聊**里发送该码；
3. 长连接回调 ingest 命中码 → **同一事务内**写绑定（库内用户 ↔ open_userid）+ 标记码已用 → 回「绑定成功」（**已落**：走长连接 `aibot_respond_msg` 透传回调 `req_id` —— 单聊回调无 `chatid`，回复不依赖寻址；见 §5）。

**投递（常态化）**

4. 单聊推送地址一律取绑定行的 open_userid；无绑定行 = 不可投递（§6）。

状态机要点：
- 绑定即激活：发码本身就是「给该机器人发过消息」，会话激活态与绑定天然同源；
- 换绑（**v1.8 修订 · 以码持有者为准**）：任一 `user_id` 命中某码 → 该 `wecom_userid` 挂到**码持有者**名下；若该企微号此前挂在别的 `user_id` = **跨用户换绑**（同事务写 `audit_logs`）；同一 `user_id` 再次命中新码 = 覆盖旧绑定（旧行处置见 §8）；
- 幂等：回调可能重复投递（官方 `msgid` 排重），绑定写库幂等；已用码再次命中 = 视为已用。

## 4. 数据模型（**已落 · 迁移 0055**）

**复用 `wecom_aibot_dm_activations`（迁移 0048）= 地址簿 + 激活登记 + 绑定三合一**

- `wecom_userid` = 回调 `from.userid` 原文（密文 open_userid）· 唯一（沿用）；
- `user_id` = 库内用户（**仅绑定行必带** —— 非绑定码的激活登记行不再回填 `user_id`，**D1**）；本方案下**可投递地址 = `bound_at` 非空的行**（绑定码命中时与 `user_id` 同事务写入）；
- `first_activated_at` / `last_message_at`（沿用）+ 新增 `bound_at`（绑定确立时间）。

**新增绑定码表 `wecom_id_binding_codes`（迁移 0055 落）**

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `code` | 6 位数字串（唯一） |
| `user_id` | 发起人（FK → `users`） |
| `status` | `pending` / `used` / `expired` |
| `expires_at` / `used_at` / `created_at` | 时限与审计 |
| `used_wecom_userid` | 实际使用该码的 open_userid（绑定/换绑排查） |

约束与规则：
- 同一 `user_id` 仅允许一个 `pending` 码（重发生效最后一条、旧码作废）；
- 生成频率限制（建议 3 次/小时/用户）；
- `code` 唯一 + 一次性；
- 明文 userid（`users.username` = SSO 口径 Casdoor Name）**保持不变，且不再作为发送地址**。

## 5. ingest 分支口径

处理条件：`cmd = aibot_msg_callback` 且 `chattype = "single"`（**已落**：非文本消息同样登记激活，只是不做码匹配 —— 与下条「未命中码的单聊消息」同口径）。

- 群聊（`chattype = "group"`）**一律不绑定**；
- 正文归一：trim → 去 `@<机器人名>` 前缀 → 提取码（形态见 D3）；
- **正文不入库、不落日志**：只记「绑定事件 + userid 掩码 + 结果」（CONTRIBUTING §12）；
- 未命中码的单聊消息：沿用现有「任意单聊消息 = 激活登记」——该行可能无 `user_id`，**不可作发送地址**（**D1 定案 2026-10-16**：仍登记，保留 846607 分流与观测）；
- 反馈（**已落：长连接 `aibot_respond_msg` + 回调 `req_id` 透传** —— E2 的 `response_url` 为备选路径；单聊回调无 `chatid`，回复不依赖寻址）：命中 → 「绑定成功」；码过期 / 码已用 → 「码已失效，请重新获取」；未命中任何码 → 不回复（防探测）。（**v1.8 修订**：删除「该 userid 已绑定 → 「已绑定」」短路 —— 旧口径下企微号若已挂在别的库内账号，用户新发之码永不消费、其页面恒显「未绑定」；现改为**跨用户换绑**：码 `used` 且持有者 = 当前库内用户时，回调重放判为幂等 → 回「绑定成功」）回执属尽力而为：失败只 warn，不影响绑定落库。

## 6. 投递前判定与失败处置

- 收件人无绑定行（**已落：按 `bound_at` 判**）→ **不发帧**，按 `permanent` 收口：`notify_deliveries.state = dead` + C5-04 站内信降级，降级前缀 = **绑定指引**（**D4 定稿 2026-10-16**：「`当前用户未绑定企业微信，请前往设置补绑`」；常量 = `DM_BINDING_DEGRADE_PREFIX`，替换原 `DM_ACTIVATION_DEGRADE_PREFIX`）；
- 有绑定行 → 正常发帧；846607 按 §7 分流；
- 页面侧：设置页显示绑定态（已绑定 / 未绑定 + 获取绑定码入口）；未绑定用户的通知相关页面给「未绑定企微」提示（`frontend/` = px 线，需求由本口径提出，见 §11）。

## 7. 846607 分流口径（激活表职责）

- 职责不变：846607 双语义（会话未激活 / 发送超频）靠激活表命中分流——命中 → `rate_limited` → `deferred`（不消耗重试次数）；未命中 → `permanent` → `dead` + 降级。现实现：`server/src/modules/notify/notify.dm.service.ts`（读表 / 分流）+ `wecom.errors.ts`（`classifyWecomErrcode`）。
- 本方案增益：绑定行必带 `user_id`，命中判定不再出现「只有密文、没有主」的模糊行。
- **核心实现变更**：单聊发送地址由 `users.username` 改为**绑定表的 `wecom_userid`**；`users.username` 只保留 SSO 与 `wecom_app` 备用通道用途。

## 8. 换机器人 / 换企业

- **地址与群绑定可复用**：`open_userid`（E6）与群 `chatid`（E7）跨机器人稳定 → 无需换绑、无需清空地址簿。
- **激活态必须按机器人重置**：「会话未激活」是针对具体机器人成立的。若换机器人后保留旧行，846607 会被判成「超频」→ `deferred` 反复延期重排（deferred 不消耗重试次数），既不 `dead` 也不降级，消息在队列里空转且用户无提示——比直接失败更糟。
  - 过渡落地（**已由 D2 取代 · 作废**）：换机器人时清空 `wecom_aibot_dm_activations`；
  - 正式方案（**D2 已拍板 2026-10-16 · 按建议 · 已落**）：给该表加机器人维度 `bot_id`（`(bot_id, wecom_userid)` 唯一）—— 随迁移 **0055** 同批落，不做「先清空再补列」的两步；落地要点见 §10.2。
- **换企业（corpid 变化）**：open_userid 与 chatid 均可能改变 → 必须重新绑定、重新绑定群。

## 9. 安全与隐私

- 绑定码 = 短时凭据：一次性、TTL、频率限制、与登录态绑定；日志只留掩码；
- 正文解析面最小化：只做码匹配，不落库、不进日志；
- 误绑防护：码被他人企微账号发出 → `used_wecom_userid` 留痕可审计；提供解绑入口（D6）；
- 群聊不绑定：E3 的 `@机器人名` 前缀正是群场景特征，解析与分支双重排除。

### 10.1 D2 说明 —— 「加 `bot_id`」的理由（2026-10-16 已拍板 · 按建议）

1. **「未激活」是 per-bot 属性**：E6 证明 open_userid 跨机器人逐字节相同，但「该用户是否和这个机器人说过话」彼此独立；只有 `wecom_userid` 一个唯一键的表，物理上无法同时表达「对机器人 A 激活了、对机器人 B 没激活」。
2. **不加 = 换机器人必现静默空转（R6）**：旧行还在 → 发送 → 新机器人返 846607（会话未激活）→ 命中激活表被误判为「发送超频」→ `rate_limited` → `deferred`；而 `deferred` **不消耗重试次数**，消息在队列里无限延期重排 —— 既不 `dead`、也不降级站内信、用户零感知，比直接失败更难排查。
3. **「清空」是把纪律当机制**：过渡法要求人记住「换机器人先清空」；本项目已换过两次机器人，漏一次即复现第 2 条。加列后新机器人天然无行 → 走 §6「无绑定行 → 不发帧 → `dead` + 站内信（绑定指引）」，正确性由结构保证。
4. **顺带三件事**：① 多机器人并存（正式 / 演示 / 培训，或同企业多应用）语义正确；② 换机器人不必整表清空（清空会连其他机器人 / 企业的绑定一起抹掉），按 `bot_id` 精确失效即可；③ 排障可回答「这个 userid 绑的是哪个机器人」，误绑 / 换绑（R2 / R3）定位成本大降。
5. **不拆表的理由**：地址（open_userid）虽跨机器人稳定，但 §6 的投递门槛是「有绑定行才发」—— 把绑定制成 per-bot 即自洽（换机器人后新 `bot_id` 无行 → 直接降级引导补绑），比「地址还在、发出去撞 846607」更安全。拆成「全局地址簿 + per-bot 激活键」要多一张表与一层 join，收益要到多机器人常态化并存才显现，现阶段属过度设计。
6. **成本**：迁移 **0055** 加一列 + 唯一键改 `(bot_id, wecom_userid)`；`WECOM_BOT_ID` 已是现成环境变量，ingest / 绑定写库原样落列；读取侧（846607 分流 `server/src/modules/notify/notify.dm.service.ts` + §7 发送寻址）加 `bot_id = 当前` 条件。改动集中在 1 张表 + 1 个 service，无契约变更、无跨模块影响。

### 10.2 D2 落地要点（**已随实现刀落 · 迁移 0055**）

- **取值**：`bot_id` = `WECOM_BOT_ID` 原文（不另建字典表、不加外键）；换机器人 = 该 env 变化即视为新机器人。
- **唯一约束**：`(bot_id, wecom_userid)` 唯一 —— 一个企微号对一个机器人只有一行；同一 `user_id` 对同一机器人再次绑定 = **换绑（覆盖旧行）**，不新增可投递地址。
- **历史行**：旧机器人已删除 → 迁移时不回填归属，`bot_id` 留 NULL，并**清空旧机器人遗留行**（NULL 行不参与投递判定）；自此不再需要「换机器人前手动清空」这条运维纪律。
- **写入侧**：ingest / 绑定写库时把当前 `WECOM_BOT_ID` 落列（与绑定码命中同事务）；`bot_id` = `WECOM_BOT_ID` 原文，读写一律 `(bot_id, wecom_userid)` 成对。
- **读取侧**：846607 分流（`server/src/modules/notify/notify.dm.service.ts`）与 §7 发送寻址一律带 `bot_id = 当前机器人` 条件。
- **可观测**：`notify_deliveries` 与日志按掩码口径记录 `bot_id`，排障可回答「该 userid 绑的是哪个机器人」。
- **落地实况（Push 247）**：`wecom_aibot_dm_activations` 加 `bot_id` / `bound_at` 两列、唯一索引由 `uq_wecom_aibot_dm_activations_userid` 改 `uq_wecom_aibot_dm_activations_bot_userid`；迁移内 `delete from wecom_aibot_dm_activations where bot_id is null` 清空旧机器人遗留行（本机演练库清 2 行）。
