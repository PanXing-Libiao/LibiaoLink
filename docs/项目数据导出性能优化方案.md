本文件讨论的“项目数据导出”以 `GET /api/v1/projects/{id}/export?format=zip` 的 ZIP 链路为主；P2～P4 的流式读取和工作簿图片注入优化同时可惠及大项目 xlsx 与页面级导出，但不在第一阶段扩大页面功能范围。

## 1. 结论与边界

- 14:19 给出的优化方向没有完整包含“附件写入 ZIP 时顺带生成缩略图，工作簿直接复用”的核心链路；当时还保留过持久化缩略图派生缓存的方向。
- 本方案将其纳入核心项，并明确用**单次导出内的临时内存结果**替代缩略图缓存。
- “不做缩略图缓存”的定义是：不落盘、不落库、不写对象存储、不跨导出或跨用户复用；单次导出内仅保留组装工作簿所必需的最终缩略图 Map，导出结束、失败或取消时立即释放。
- 附件仍按现有顺序和压缩策略写入 ZIP。缩略图捕获器只旁路读取字节，不改变源流、附件字节、ZIP 条目顺序、大小、SHA-256、manifest 或审计口径。
- 同一 `fileId` 的缩略图只生成一次；同一附件因不同目录重复入包时，ZIP 打包行为保持不变。
- 本优化不能通过减少附件并发或取消审计来换取速度；安全、权限、下载审计和资源上限保持不变。

## 2. 当前基线与问题

截至 2026-11-09，ZIP 项目导出的主要链路位于 `server/src/modules/project-export/project-export.service.ts`：

1. `exportProjectArchive()` 收集项目数据并规划附件。
2. `writeProjectArchiveAttachments()` 逐个调用 `getObjectStream()` 读取附件并写入 ZIP。
3. 附件全部写完后，才计算工作簿所需图片 ID，并由 `loadImages()` 再次调用 `getObject()` 读取图片。
4. `thumbnailImage()` 生成 `360×270`、JPEG 质量 72 的缩略图。
5. 工作簿生成后，由 `project-export.xlsx-images.ts` 重写 xlsx ZIP，注入图片、DrawingML、关系文件和 Content Types。

当前样本约有 164 个附件、160 张工作表缩略图：

- 理论对象存储读取约 324 次。
- 理论读取量约 141 MB。
- 附件读取与缩略图读取之间存在同一张图片被下载两次的问题。

现有图片预算保持不变：最多 250 张、单张原图最多 8 MB、缩略图来源总字节最多 80 MB；单文件附件上限 200 MB，附件总量上限 2 GB，最多 3,000 个附件文件。

## 3. 目标数据流

目标链路为：

1. 收集项目数据。
2. 在写附件前计算工作簿所需的 `imageIds`，每个单元格仍只取前 4 张。
3. 建立本次导出需要捕获缩略图的 `fileId` 集合。
4. 附件逐项流式写 ZIP；命中图片 ID 的附件在旁路有界捕获字节。
5. ZIP 条目写入成功后，从同一份字节生成最终缩略图，放入本次导出临时 Map，释放原图缓冲。
6. 工作簿直接使用临时 Map，不再对已捕获图片调用 `getObject()`。
7. 导出结束、失败或取消时释放临时 Map 和全部临时文件。

## 4. 实施阶段

### P0：建立基线与可观测性

状态：待开始。优先级：最高，先于代码优化。

实施内容：

- 在导出日志中增加分阶段耗时：数据读取、附件对象存储读取、附件写 ZIP、缩略图生成、工作簿生成、工作簿图片注入、ZIP 收尾、审计。
- 增加计数：附件数、`getObjectStream` 调用数、`getObject` 调用数、实际读取字节数、缩略图命中 / 缺失数、重复 `fileId` 数、输出字节数。
- 使用当前真实大项目与合成 20,000 行数据进行基线记录；日志不得包含对象键、Secret 或完整敏感文件内容。
- 将基线数据回填到本文件 §8。

出口判据：能够分别看到附件读取、缩略图二次读取、图片解码、工作簿写入和图片注入的耗时与调用次数。

### P1：ZIP 图片附件一次读取并复用缩略图

状态：待开始。优先级：最高，核心改动。

实施内容：

1. 在 `exportProjectArchive()` 写附件之前计算 `projectArchiveImageIds()` 的结果，并建立 `neededThumbnailIds`。候选条件至少包括文件引用存在、对象键存在、MIME / 文件名表明可能为图片、已知大小不超过 8 MB。
2. 将 `neededThumbnailIds` 和本次导出临时图片 Map 传入 `writeProjectArchiveAttachments()`。
3. 附件仍按现有 `plan.files` 顺序串行写入；只对状态为 `included` 且命中 `neededThumbnailIds` 的附件开启捕获。
4. 在源流与 ZIP 写入器之间加入有界透传捕获器：
   - 原字节不加修改地交给 ZIP writer。
   - 只缓冲当前这一张图片，最大 8 MB。
   - 先检查 PNG / JPEG / GIF 文件头，不单纯信任扩展名。
   - 文件头不支持时立即停止缓冲，附件继续正常写入。
   - 超过 8 MB 时停止缓冲并丢弃，不生成缩略图。
   - 必须保持背压、取消信号、流错误与临时文件清理语义。
5. ZIP 条目写入成功后，使用刚捕获的完整字节生成 `360×270` JPEG 缩略图，质量 72；生成逻辑复用现有 `thumbnailImage()` 行为。
6. 仅为成功生成的最终缩略图建立 `fileId → ExportImage` 临时 Map；原始字节缓冲立即释放。若现有缩略图逻辑回退为原图，也仍受 80 MB 图片总预算约束。
7. 工作簿阶段直接使用该 Map，删除 ZIP 导出路径中已捕获图片的第二次 `loadImages()` / `getObject()` 读取。
8. 同一 `fileId` 只生成一次缩略图；第一次捕获失败时允许后续同名附件重试，不把失败的 ID 永久标记为完成。
9. 缺失、读取失败、被跳过、超过大小限制或缩略图生成失败时，工作簿继续写现有「（附图缺失）文件名」占位，不为补图重新访问对象存储。
10. 保持 250 张 / 单张 8 MB / 总计 80 MB 上限；被总量限制跳过的附件不额外读取。

内存边界：

- 当前原图捕获缓冲最多约 8 MB。
- 最终缩略图通常每张约 21 KB，250 张约 5 MB 量级。
- 缩略图未缩小而回退原图时，仍受现有 80 MB 图片总预算约束。
- 不新增临时盘或对象存储占用。

出口判据：

- 每个实际入包且需要缩略图的图片附件只发生一次对象存储读取。
- ZIP 导出路径不再为工作簿图片调用 `getObject()`。
- 复用同一份字节生成的缩略图数量、位置和缺图占位与改动前一致。

### P2：去掉日报双扫

状态：待开始。优先级：中。

实施内容：

- 当前流式导出先完整扫描日报获取 ID 和总数，再读取日报生成行。
- 增加导出专用日报总数查询，只读取 `total`，不扫描日报正文。
- 问题先按 `sourceReportId` 分组；日报正文只完整读取一次并逐行消费对应问题。
- 未能对应到任何导出日报的问题，在日报读取完成后按现有孤立问题规则追加。
- 保持日报升序、每篇日报内问题顺序、草稿日期和问题字段口径不变。

出口判据：日报正文只发生一次完整扫描；问题归属和行序与优化前逐行一致。

### P3：导出专用批量读取

状态：待开始。优先级：中。

实施内容：

- 公共 API 仍保持每页最多 200 条，不修改 Zod / OpenAPI 契约。
- 仅增加服务内部导出读取接口，使用约 1,000 条一批或游标读取；实际批量以各领域查询能力和数据库实测为准。
- 各类总数只查询一次，避免每页重复统计。
- 任务导出跳过不需要的附件摘要查询。
- 干系人权限和可见项目集在单次导出中只解析一次，不随分页重复解析。
- 文件、日报、问题、变更、干系人逐批返回，不把全部业务行数组装入内存。

出口判据：导出读取页数下降，内存峰值不高于现有边界，公共分页契约无变化。

### P4：降低工作簿图片注入成本

状态：待开始。优先级：中。

实施内容：

- 优化 `server/src/modules/project-export/project-export.xlsx-images.ts` 的 `injectWorkbookImages()`。
- 未修改的 ZIP 条目直接复制原压缩字节，不再全部解压后重新压缩。
- 只解压、改写工作表 XML、关系文件和 Content Types。
- 去掉图片注入路径中实际未使用的工作簿 SHA-256 重算。
- 无法直接复制的条目再回退到原有解压、重压缩流程。
- 保持临时工作簿替换、权限 `0600`、图片注入失败回退和清理逻辑不变。

出口判据：未修改 XML 条目不重新压缩；工作簿可正常打开，图片、关系、超链接和媒体复用与改动前一致。

### P5：有实测收益后再执行的选项

状态：待定。未取得基线证据前不得直接实施。

候选项：

- 附件预取最多 4 路，但必须按原附件顺序写 ZIP，不能改变包内顺序；任何预取都只保留在途流，不落盘、不跨导出复用。
- 对比 deflate level 6 / 3 / 1 的耗时和输出体积，只有压缩率可接受时才降低等级。
- 评估 Node 原生 `zlib.crc32`，减少大附件写入时的 JavaScript CRC 计算开销。
- 不改变当前单导出槽位与 429 并发策略；这是独立的并发治理问题。

## 5. 正确性与边界约束

- ZIP 内原附件字节、附件大小、SHA-256、条目顺序和 manifest 必须与优化前一致。
- 文件缺失、对象读取失败、超过单文件限制、附件总量超限、导出取消和临时目录清理均保持现有降级行为。
- 附件规划已判定为 `missing` / `skipped` 的项目不得为了生成缩略图额外读取。
- 图片必须按文件头确认格式；不支持的伪装图片不得进入工作簿媒体。
- 每个单元格最多取前 4 张附图；跨 Sheet 媒体复用保持现有行为。
- 文件链接、工作簿中文表头、Sheet 顺序、列顺序、页面级导出列集合均不变。
- 不新增数据库表、字段、DDL、迁移、任务队列、环境变量、第三方依赖或 Secret。
- 不做持久化缩略图缓存，不引入缩略图缓存目录、TTL、清理任务或跨用户复用。

## 6. 验证方案

自动化测试：

- 在 `server/test/project-export.test.ts` 增加捕获器透传、8 MB 截断、文件头识别、非图片停止捕获和流错误传播测试。
- 断言需要缩略图的附件只调用一次 `getObjectStream()`，ZIP 图片路径不调用 `getObject()`。
- 断言 ZIP 内附件字节、大小、SHA-256 和 manifest 与优化前一致。
- 断言缩略图数量、每格最多 4 张、多 Sheet 媒体复用、缺图占位和同一 `fileId` 去重正常。
- 覆盖附件跳过、对象缺失、缩略图生成失败、导出取消和临时目录清理。
- 回归 `server/test/page-export.test.ts`，确认页面级导出的列、预览和流式生成不受影响。

性能验证：

- 先用 P0 基线记录真实样本的调用次数、读取字节和分阶段耗时。
- 优化后使用同一项目数据复测，至少对比 `getObjectStream` 次数、`getObject` 次数、对象存储读取字节、缩略图生成次数、导出总耗时和 API 内存峰值。
- 当前样本目标：对象存储读取约 324 次降至约 164 次，读取量约 141 MB 降至约 70.6 MB；图片解码和缩放次数不得增加。
- 若真实项目存在重复附件路径，以实际附件入包次数为准，不强行宣称固定为 164 次。

门禁：

- server 定向测试、全量测试、typecheck、build、边界检查通过。
- `git diff --check` 通过。
- 检查 diff 不包含对象键、Secret、调试输出、临时文件或未批准依赖。
