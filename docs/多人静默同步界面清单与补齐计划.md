## 1. 梳理依据与结论边界

以当前 `wmj` 工作区的 `App.tsx`、`useHashRoute.ts`、全部页面及其子组件调用关系、前端 API 封装和对应服务端写入口为依据。需求文档用于核对业务口径；其中“后端尚未落地”“编辑只落原型内存”等历史文字不能替代当前代码事实。

内置浏览器运行真实前端，后端使用完全虚构的隔离接口，查看了 7 类路由、项目详情 7 个主视图、日报 4 个子视图、工作台及问题子视图、九阶段模板导航、项目文件与回收站两栏，以及代表性的项目表单、任务抽屉三页、添加任务浮层、文件下拉、问题抽屉、干系人编辑、便签编辑。它确认入口和界面形态，不代表真实后端的全部增删按钮已经验收。

图片/PDF/ONLYOFFICE/CAD 预览分支、变更全文和导出通过源代码核对。本轮没有接真实对象存储、转换 worker、ONLYOFFICE、Casdoor 登录表单或 CAD 文件验证这些外部链路，也没有做生产十人容量压测。

当前有 **7 类应用路由**，并非只有顶部导航的 4 个入口。项目详情、工作台、任务抽屉还包含多层界面。“已经接入”在下表只表示主读面已订阅自动回读，不能据此宣称所有交互、缓存和并发草稿都已覆盖。

## 4. 已确认缺口与推断风险

### 4.1 已确认的代码事实

1. `liveSync.ts` 的全局暂停条件包含任何 dialog、行内浮层、聚焦输入、拖动及本地写入。打开只读文件预览也会暂停所有普通同步；这保守地保护编辑，但不是各局部区域独立同步。
2. `AuditLogPage.tsx` 没有同步订阅；项目筛选选项也只初次读取。只补“成功写请求”事件仍漏掉下载 GET、拒绝留痕及 worker 写入。
3. `TaskDrawer.tsx` 的附件 effect 依赖 projectId/taskId/filesTick；`StageAddCard.tsx` 的节点/模板 effect 依赖阶段/重试；`ChangeDetailModal.tsx` 依赖 changeId/retry。这些读面没有独立实时失效。
4. `fileApi.ts` 的预览 URL 以 fileId 或 fileId@versionId 缓存，远端 `files` 提示没有接到该缓存。清单变化不等于缩略图和后续预览已更新。
5. 人员目录已有 users 订阅，但现行发布映射匹配 `/api/v1/users`；真正停用/启用/删除和组织同步走 `/internal/users/*`、`/internal/org-sync/run`，不在映射中。普通周期回读仍可能更新目录，但没有这些路径的即时提示。
6. `permissions.ts` 成功后缓存 Promise 到应用结束；`App`、`AppHeader`、回收站各持自己的权限状态，尚无统一的更新订阅，后端部门画像另有 10 秒缓存。`RoleService` 固定返回全量能力基线，实际项目范围与写能力由部门规则裁决。
7. 个人偏好明确被发布映射排除；`MyPlanBoard` 无同步订阅，整板写入只在本窗口串行。服务端偏好是先读取、JS合并、再整行 upsert，没有跨请求比较版本。
8. 日报填写仅保存 draftId；暂存/提交时从最新 reportsRef 查 version。项目归档路径也会读取 latest.version 给表单字段 PATCH。二者都需要明确保留编辑基线，不能笼统写“所有草稿均绑定旧版本”。
9. 服务端实际蓝图前缀为 `/api/v1/blueprint`，现映射写成 `blueprints`。前端没有蓝图编辑入口，这属于现有映射的兼容遗漏，不是漏了一张已上线的页面。
10. 项目/任务/日报/联系人/目录若只读首个200条，文件读取也有分页上限。自动同步沿用该读面范围，并不会自动获得所有数据库记录；不能以“接入了同步”替代对截断提示和实际容量的确认。

### 4.2 从代码推断、尚未实测的风险

- 已暂存日报在输入失焦后可回读到新 version，而旧表单文本没有同步更新；随后使用新 version 提交可能掩盖并发修改。远端删掉草稿后，查不到 draftRow 的分支可能改走 POST。这是代码路径推断，本轮未用真实后端重现。
- 两个同账号窗口同时保存便签会按整板覆盖；同时改不同偏好键也可能在“读旧行→覆盖写”之间丢掉另一键。这是明确的并发设计缺口，不等于已观察到生产数据丢失。
- 甘特图范围由任务最早/最晚日期推导；只恢复像素滚动可能仍使原来看的日期变掉。看板、地图列表也缺专用卡片/日期锚点，需浏览器验证。
- 每个订阅的单飞不等于全应用单飞。项目页同时有头信息、任务、日报等读面，回收站 / 项目文件和工作台又逐项目并行；十人连续修改时可能放大请求。现有200次/1000次本地回放证明指定场景稳定，不能外推到任意项目数量。

## 5. 方案比较与选择

### 5.1 共享业务数据

| 方案 | 对本项目的适配 | 结论 |
| --- | --- | --- |
| 只靠固定短周期轮询 | 所有页面可统一补读，但空请求多，编辑/缓存/并发问题仍存在 | 保留30秒补偿，不作为主要通道 |
| 现有SSE提示＋鉴权回读＋局部草稿保护 | 已有通知连接与PG广播桥；HTTP写接口和乐观锁继续使用；补齐各读面即可 | 本次继续采用，完善粒度和失效链 |
| 改用WebSocket＋全量协同状态 | 能支持双向协同光标/字符编辑，但目前是独立表单提交，没有此需求 | 本次不更换通道、不加依赖 |

SSE支持命名事件及断线重连，适合这里的服务端单向提示；同浏览器多标签的HTTP/1连接限制需要在最终部署验证，不能拿“十个不同用户连接”替代“十标签”验证。[MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。上述选择是结合本仓库架构的判断。

### 5.2 本人偏好与便签

| 方案 | 能覆盖的范围 | 结论 |
| --- | --- | --- |
| 仅BroadcastChannel | 同源且同存储分区的窗口；不能跨设备，也不解决后端覆盖写 | 可选优化，不作主通道 |
| 本人定向SSE提示＋周期补读 | 同账号各窗口/设备；可复用既有recipientId扇出 | 采用，先补版本比较与原子更新 |
| 广播个人偏好/整板给所有在线用户 | 接收者范围错误，也会触发无关UI变化 | 不采用 |

BroadcastChannel的作用范围见[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API)。采用定向提示是本项目判断，个人内容仍通过本人鉴权读接口读取。

React会根据组件位置和key保留或重置状态，故保护草稿需要稳定组件身份及独立基线，而非禁止所有数据渲染。[React状态保留](https://react.dev/learn/preserving-and-resetting-state)。权限状态的前端更新只改展示，服务端仍按项目既定开关和逐请求策略裁定。[OWASP授权原则](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

偏好更新应在数据库内对当前值合并，并在同一受保护写入中比较基线；现有upsert的原子性并不能挽救已在JS里合并好的旧整行。[PostgreSQL INSERT/ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html)。

## 6. 按依赖实施的补齐计划

### P0：先保证草稿和实际数据不会被悄悄覆盖

1. 建立显式的编辑状态：对象id、开始编辑的version、脏字段、保存中状态，与后台读快照分开。普通只读区域可以更新；受保护对象在编辑/拖动期间保留位置和基线。不能只凭焦点判断页面内草稿是否存在。
2. 先接日报填写、项目编辑/归档、任务抽屉/行内编辑、日报问题弹窗和模板草稿。原有带version的提交继续使用草稿基线；409时保留文字和选区，提示远端变化，由用户决定取最新后重新编辑。对象被删时保留未提交文字并禁止原保存，不能默默新建或关窗。
3. 归档含字段编辑时，先按原基线保存；仅本人成功保存产生的新版本可用于后续归档确认。再次补读发现他人版本变化要重新确认，不能自动将旧表单绑定fresh.version。
4. 本人偏好先改成数据库内按键原子合并，避免不同键互相覆盖；为整板和常用筛选增加服务端可比较的基线标识和冲突响应。标识可存于既有JSONB元数据并在事务内比较/递增，契约和旧客户端兼容窗口须同时明确；不先上自动回读再补保护。
5. 便签初次预置/旧键迁移也必须比较“服务端仍为空”的基线，避免两个新窗口各自预置或迁移覆盖。
