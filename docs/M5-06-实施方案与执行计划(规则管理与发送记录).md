## 2. 目标与验收口径

### 2.1 功能目标

1. **C2-01**：管理员可查看 10 条内置规则；可启停；可在允许范围内配置渠道与收件人；可试运行并看到逐条条件求值结果。
2. **C2-07 / C5-03**：任意一次 `notify.message` / `notify.group` 产出都有消息级记录；外部渠道的每次尝试都有尝试明细；发送对象、渠道、时间、结果可查；成功发送的企微消息不会因 outbox 清理而丢失留档。
3. **S7-5**：规则启用 / 变更 / 停用时，`automation-schedule.job` 与规则表、规则版本保持联动；不再依赖人工插行。
4. **C2-12**：运行记录可解释 —— 条件 field / op / expected / actual / passed，窗口键、跳过原因、动作与消息快照均可回溯。
5. **安全**：规则管理、发送记录、重发均受权限键控制，变更和重发写审计；目标地址、绑定码、Secret 不出现在日志或读面明文中。

### 2.2 不可破坏的口径

- 规则触发条件、内置模板正文、`groupBy`、`template` 码默认只读；不得在规则管理页改写逐字文案。渠道和收件人只能在内置白名单内调整。
- 规则保存使用 `version` 乐观锁；版本冲突返回 409 `VERSION_CONFLICT`，不得静默覆盖。
- 发送记录是**归档**，不是 outbox 的镜像；outbox 清理只把 `outbox_id` 置空，不删除消息 / 尝试记录。
- 重发创建新的 outbox 行，不覆盖原消息或原尝试；重发仍走限速、每日上限、绑定态与 C5-04 降级。
- 站内信（`inbox`）不进入外部重发链路；`wecom_app` / `wecom_aibot` / `wecom_group` 才允许重发。

## 3. 数据模型与事务口径

### 3.1 `automation_rules`

**定位**：规则配置的权威来源。内置规则由种子幂等写入；代码常量只保留为种子 / 金标来源，不再是运行时读取源。

建议字段：

| 字段 | 类型 | 口径 |
|---|---|---|
| `id` | uuid PK | 规则内部 id；运行记录按此关联 |
| `code` | text unique | 规则码（内置 R02 ~ R07 / A01 / A02 / A08 / A14；A03 不恢复） |
| `name` | text | 展示名；一期只读 |
| `built_in` | boolean | 是否内置；一期管理面只含内置规则 |
| `enabled` | boolean | 启停开关 |
| `trigger` | jsonb | 规范化 `AutomationTrigger` |
| `conditions` | jsonb | 规范化条件数组；可解释性来源 |
| `actions` | jsonb | 规范化动作数组；渠道 / 收件人可配置，模板与动作类型只读 |
| `version` | integer | 每次保存 +1；乐观锁 |
| `created_by` / `updated_by` | uuid null | 操作人；系统种子为 null |
| `created_at` / `updated_at` | timestamptz | 审计时间 |
| `deleted_at` | timestamptz null | 软删；内置规则一期不允许删除 |

约束与索引：

- `code` 唯一；`deleted_at` 为空时参与管理读面。
- `version >= 1`；`enabled` 默认 `false`。
- `trigger` / `conditions` / `actions` 由服务端按共享 schema 解析，禁止存任意未知 JSON。
- 建议 `(enabled, deleted_at)` 与 `code` 索引；本期规则量小，不引入复杂分页索引。

### 3.2 `automation_runs`

**定位**：每次规则 × 实体 × 窗口的求值留痕，供 C2-12 与运营排障；不做投递状态机。

建议字段：

| 字段 | 类型 | 口径 |
|---|---|---|
| `id` | bigserial PK | 运行记录 |
| `rule_id` | uuid null FK | 规则删除后置 null；保留 `rule_code` 快照 |
| `rule_code` | text | 规则码快照 |
| `rule_version` | integer | 求值时的规则版本 |
| `source` | text | `event` / `schedule` |
| `topic` | text null | 事件主题；调度为 null |
| `window_key` | text null | 调度窗口键 / 事件版本窗口 |
| `entity_type` | text null | task / report_slot / project_day / todo / stage |
| `entity_id` | text null | 实体 id |
| `dedupe_key` | text unique | 运行幂等键（见下） |
| `status` | text | `hit` / `skipped` / `failed` |
| `skip_reason` | text null | `disabled` / `subject_mismatch` / `window_mismatch` / `not_matched` / `recipient_missing` / `template_missing` / `duplicate` / `event_too_old` |
| `conditions` | jsonb | 逐条条件求值明细（field / op / expected / actual / passed） |
| `actions` | jsonb | 动作快照（channel / recipient / template / groupBy） |
| `messages` | jsonb | 产出消息快照（recipient / channel / template / dedupeKey / title / body） |
| `error` | text null | `failed` 时的可读原因 |
| `created_at` | timestamptz | 写入时刻 |

运行幂等键：

- 事件：`event:<来源 outbox dedupeKey>:<ruleCode>:<entityId>`；
- 调度：`schedule:<ruleCode>:<entityId>:<windowKey 或 '-'>`。
- `dedupe_key` 唯一，重放时 `insert ... on conflict do nothing`；命中已存在即不再产出。

事务口径：

- **调度路径**：`automation_runs` 写入、outbox 追加与 `jobs.last_run_at` 推进必须在 `JobRunContext.tx` 同一事务；任一失败整体回滚。
- **事件路径**：`automation-wiring` 的事件 handler 也要开启数据库事务（主体读取可传 tx），在事务内写运行记录与 outbox；失败交回 outbox 重试。不得只依赖「运行记录已写」而丢失 outbox。
- `failed` 运行记录只在可确定失败且已决定终止当前求值时写；可重试的数据库异常直接抛出，让 outbox / job 按既有策略重试，避免把暂时故障记成永久失败。

### 3.3 `jobs` 增量

在现有 `jobs` 表只追加：

- `dedupe_key text null`；唯一索引（PostgreSQL 允许多个 null，历史行不受影响）。
- 内置调度规则使用 `dedupe_key = 'automation-schedule:' || ruleCode`。
- `payload = { ruleCode, ruleVersion }`；`cron` 取规则 trigger.cron；`kind = 'automation-schedule.job'`。

`JobsStore` 增加 upsert / reconcile：

1. 新建调度规则：插入 job，`status = pending`、`run_at = now()`、`last_run_at = now()`（避免补发启用前窗口）。
2. 启用 / 重新启用：job 置 `pending`，`run_at = now()`，`last_run_at = now()`；`attempts = 0`、`last_error = null`。
3. 规则更新：更新 payload 的 `ruleVersion` 与 cron；不重置 `last_run_at`（避免重复补发）。
4. 停用 / 软删：job 置 `done`；保留行用于排障。
5. 历史遗留的 `automation-schedule.job`（payload 无 `ruleCode`）：handler 在一期兼容「执行全部启用调度规则」；部署时先新建 per-rule job，再将已验证的旧通用 job 置 `done`。不得让旧 job 与新 job 长期并行空转。

### 3.4 `notify_delivery_messages`

**定位**：消息级发送归档，覆盖 `notify.message` 的 inbox / 企微应用 / 单聊 aibot 与 `notify.group`；尝试级结果仍落 `notify_deliveries`。

建议字段：

| 字段 | 类型 | 口径 |
|---|---|---|
| `id` | bigserial PK | 消息记录 |
| `outbox_id` | bigint null FK | 来源 outbox；清理后 `set null`，记录不删 |
| `source_dedupe_key` | text unique | 来源 outbox dedupeKey；归档幂等 |
| `topic` | text | `notify.message` / `notify.group` |
| `channel` | text | inbox / wecom_app / wecom_aibot / wecom_group / email |
| `recipient_id` | uuid null | 站内信 / 企微收件人 id（如有） |
| `recipient_label` | text null | 展示名或掩码目标；不得存 Secret |
| `title` / `body` | text | 最终标题 / 正文快照 |
| `template_code` | text null | 模板码 |
| `rule_code` | text null | 来源规则码 |
| `ref_type` / `ref_id` | text null | 关联对象 |
| `payload` | jsonb | 原始规范化载荷快照；重发所需 projectId / group 寻址等字段从此取 |
| `resend_of_message_id` | bigint null FK | 重发消息指向原消息；原消息不覆盖 |
| `metadata` | jsonb not null default `{}` | 操作 / 回填 / 迁移等附加标记（不得放 Secret） |
| `last_state` | text | `pending` / `sent` / `failed` / `deferred` / `dead` |
| `attempt_count` | integer | 尝试次数（不含 deferred 的计划尝试可按现有口径累计） |
| `last_error` | text null | 最近失败 / 延期原因（已掩码） |
| `sent_at` | timestamptz null | 首次 API 受理时刻 |
| `created_at` / `updated_at` | timestamptz | 归档时间 |

`notify_deliveries` 只追加 `message_id bigint null`，并在写入尝试时回填；历史行允许 null。消息归档不受 outbox 清理与 `notify_deliveries` 行保留策略影响。

### 3.5 归档写入与历史回填

- 外部渠道：在 `NotifyAppService` / `NotifyDmService` / `NotifyGroupService` 收到合法 outbox 载荷后、第一次发送 / 写入尝试前，先 `ensureMessage` 落消息归档；随后每次尝试写 `notify_deliveries` 并带 `message_id`。
- 站内信：`NotifyService.deliverOnce` 在 `notifications` 落行同一事务内写消息归档；合并子行保留消息归档，读面通过 `notifications.merged_into_id` 展示「已合并」。
- C5-04 降级副本：以 `:c504` 幂等键单独落一条 inbox 消息归档，可追溯来源。
- 归档失败：外部渠道必须回滚本次投递并交回重试，不得「发出去了但没有留档」；inbox 同理。非法载荷无法形成可信消息字段时才直接 outbox dead，并保留 outbox 错误。
- 回填：新增一次性、幂等脚本 `scripts/m5-06-backfill-delivery-messages.mjs`；外部渠道从仍存在的 `notify_deliveries` + `outbox_events` 还原，站内信从 `notifications` 还原；只补 `message_id is null`，不覆盖已有记录。outbox 已清理的部分允许保留为历史缺口并登记。

## 4. 规则管理与调度设计

### 4.1 运行时读表

`listEnabledRules()` 改为读 `automation_rules`：

1. 查询 `enabled = true and deleted_at is null`；
2. 用共享 `AutomationRuleSchema` 逐行解析；
3. 任一行非法 → 记录错误并抛错（fail closed），不得跳过该行后继续发通知；
4. 表为空 → 返回空集并打一次显著告警（提示 seed 未执行），不得回退 `BUILTIN_RULES`；
5. 事件与调度共用同一读表实现，签名保持 `Promise<AutomationRule[]>`。

种子：

- 新增 `database/seeds/automation-rules.mjs`，以 `BUILTIN_RULES` 为唯一数据源，按 `code` 幂等插入缺失行；**不覆盖已有 enabled / actions / version**。
- 首次写入时 `enabled` 与代码常量一致（当前仅 R02 / R03 / R05 为 true）；后续以库内值为准。
- 种子同时创建 / reconcile 调度 job；在 CI 与部署流程中显式执行，禁止依赖 API 启动时偷偷写库。
- 迁移号必须在实施时重新检查，不得预占；当前最高为 `0059`，但每个切片开工前重新以仓库最新迁移为准。

### 4.2 管理接口行为

- 管理面固定返回 10 条内置规则；R01 不进入管理列表（由 M4-04 变更事务处理）；A03 不出现在枚举与列表。
- 允许修改：`enabled`，以及各动作的 `channel` 和 `recipient`（必须在白名单和动作允许范围内）。
- 只读：`code`、`name`、`trigger`、`conditions`、`kind`、`template`、`groupBy`、内置规则的主体类型。
- 保存时服务端把动作与种子 / 数据库当前版本比较：只接受允许字段变化；模板码变化、条件变化、动作数量变化一律 400 `VALIDATION_FAILED`。
- 成功保存：同事务更新规则、`version + 1`、审计、job payload / 状态 reconcile。
- 规则停用：不删除规则行，不删除 job 行；job 置 `done`，运行时不再产出。
- 管理接口不提供内置规则物理删除；自定义规则编辑器不在本期。

### 4.3 试运行

试运行是**只读**操作：不写生产 `automation_runs`、不写 outbox、不触发投递、不写审计。

请求体：

- `businessDate`：可选 `YYYY-MM-DD`，缺省为当前 Asia/Shanghai 业务日；
- `entityId`：可选；事件型规则必须给，用于定位单个主体；调度型可省略，按窗口主体池评估。

响应：

- `businessDate`、`evaluatedCount`、`matchedCount`、`skippedCount`、`truncated`；
- `messages[]`：规则码、实体 id、窗口键、channel、recipient、template、title、body、dedupeKey；
- `skipped[]`：reason、ruleCode、entityId、windowKey、conditions[]。

上限：调度型最多评估 100 个主体；超出置 `truncated = true` 并返回已评估部分。事件型未给 `entityId` 返回 400；实体不存在或不可见返回 404（不泄露存在性）。

### 4.4 运行记录读面

- 列表筛选：`ruleCode` / `status` / `source` / `topic` / `from` / `to` / `entityId`，按 `createdAt desc, id desc` 稳定分页。
- 详情完整返回条件求值明细、动作快照、消息快照与错误。
- 运行记录与发送记录通过 `dedupeKey` / `ruleCode` 可关联，但不把运行记录当作发送结果。

## 5. 发送记录与重发

### 5.1 记录层级

1. **消息级** `notify_delivery_messages`：一次 outbox 消息一行，保存最终标题 / 正文、渠道、收件人和来源；这是 C2-07 列表与 C5-03 留档的主表。
2. **尝试级** `notify_deliveries`：每次外部投递尝试一行，按 `message_id` 归属消息；保留 `sent` / `failed` / `deferred` / `dead` 与错误原因。
3. **站内信行** `notifications`：仍然是收件箱读面；消息归档额外保存一份，保证 outbox 清理后仍能查发送事实。
4. **状态**：消息级 `last_state` 随尝试更新；列表支持按最新状态筛选。`deferred` 表示尚未发起或已延期，不是成功。

### 5.2 读面口径

- 列表：`channel` / `lastState` / `ruleCode` / `recipientId` / `from` / `to` / `q`（标题或正文包含）筛选，`createdAt desc, id desc` 分页。
- 详情：消息正文、模板、关联对象、来源 ruleCode、全部尝试；目标地址只回掩码，不返回 Secret / 完整 chatid / 完整 userid（排障全文只在受控库内）。
- 时间：统一 ISO8601；展示层按 Asia/Shanghai。
- 可见性：管理员读面，不按项目成员泄漏未授权内容；如后续需要项目范围，另做数据范围过滤，不在本期临时拼接。
- 归档不作为“已读 / 已处理”的替代；收件箱状态仍以 `notifications` 为准。

### 5.3 重发语义

- 仅允许 `wecom_app` / `wecom_aibot` / `wecom_group`；`inbox` 不重发，`email` 未落地不重发。
- 仅允许消息最新状态为 `failed` 或 `dead`；`pending` / `deferred` / `sent` 一律 409，避免并发重发或在途重复。
- 请求必须携带 `Idempotency-Key`；同一 key 重试返回同一结果。缺失 key 返回 400 `VALIDATION_FAILED`（本卡不引入新的泛用错误码）。
- 成功重发：基于原 `payload` 生成**新 outbox 行**，新 `dedupe_key = 原 dedupeKey + ':resend:' + 请求幂等键哈希`；原消息、原尝试和原消息状态不变，另落一条新消息归档（`resend_of` 元数据）。
- 重发仍走原主题的投递消费者、限速、每日上限、绑定态、C5-04 降级与失败收敛；不得绕开 outbox 直接调企微。
- 重发写审计：建议 `objectType = notify_delivery`，`action = update`，metadata 记录 `operation=resend`、`sourceMessageId`、`newOutboxDedupeKey`。是否将 action 扩为 `resend` 由 D8 定；不改变审计不可改删的口径。
- 重发请求不得改写正文、收件人或渠道；如需改配置，先修规则 / 绑定，再重发原消息。

### 5.4 保留与回填

- 消息级归档默认不自动清理，优先级高于 outbox 的 90 天 done 清理；先观察容量与索引增长，再决定保留策略（若未来设置保留期，必须同步产品 / 审计口径，不得静默删除）。
- `outbox_id` 使用 `on delete set null`；`notify_deliveries.outbox_id` 现有语义保持，不因新增 `message_id` 改变。
- 回填脚本只补缺失链接，不伪造历史成功状态；无法还原的旧行明确标为 `message_id = null`，读面以“历史仅尝试级记录”提示。
- 归档表与 `notify_deliveries` 的索引至少覆盖 `(channel, created_at desc)`、`(last_state, created_at desc)`、`(rule_code, created_at desc)`、`(message_id, id)`。

### 6.3 错误与边界

- `404`：规则 / 运行 / 消息不存在或无权访问；不得区分“存在但无权”。
- `409 VERSION_CONFLICT`：规则保存版本冲突。
- `409`：规则动作试图修改只读字段；重发消息不在 `failed` / `dead`；重发消息不是外部企微渠道。
- `400 VALIDATION_FAILED`：试运行事件型规则缺 entityId、请求体非法、重发缺幂等键。
- `422` 仅用于契约明确可修复的求值输入错误；数据库 / 网络错误按 500 + traceId，不把内部异常文本原样返回。
- 所有新端点写请求启用现有 CSRF / session 守卫；管理动作不得仅靠前端按钮隐藏。
