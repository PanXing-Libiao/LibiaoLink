## 3. 目标形态（设计定稿要点）

### 3.1 渠道与路由

- 新渠道值 **`wecom_aibot`**（P1 定案）承载单聊 aibot；`wecom_app` 枚举值 / 路由分支保留（D1 / D5）。
- 4 条内置规则渠道值由 `wecom_app` 切至新值（R02 / R07 / A01 / A14）；产出仍走 `notify.message` 主题，幂等键镜像 `:app` 先例（建议 `:aibot` 后缀；以实现段为准）。
- `DELIVERABLE_CHANNELS` 加入新值（否则产出层按未落地渠道跳过 / 投递层按白名单外收口）；`OutboxModule` 路由新增分支 → `NotifyDmService`。
- A01 合并模板：`MERGED_TEMPLATE_SPECS` 增 `A01|wecom_aibot` 键（键格式 = ruleCode + 竖线 + channel，同现有 `A01|wecom_app`；R07 走 rule 级回退，沿用）；**模板码一期保名换渠道**（P1 定案）—— 4 条规则模板码不更名，`docs/rules` 两本文案文件与 `automation/README.md` 的渠道括注随契约段改 aibot 口径。

### 3.2 激活表与回调 ingest

- 新表（建议 `wecom_aibot_dm_activations`）：`wecom_userid` 唯一（回调 from.userid 原文）+ `user_id`（可空 · FK → users · 按 `users.username` 反查回填）+ `first_activated_at` + `last_message_at`；形状护栏沿用群表风格（DDL 随迁移段）。
- **绑定码口径修订（v1.13 · 2026-10-16 · Push 247）**：该表已扩为「地址簿 + 激活登记 + 绑定」三合一 —— 加 `bot_id`（=`WECOM_BOT_ID` 原文，唯一键由 `wecom_userid` 改 `(bot_id, wecom_userid)`）与 `bound_at`（**非空 = 可投递地址**）；`user_id` 不再按 `users.username` 反查（**D1**：非绑定码的激活登记行不留 `user_id`）；另立绑定码表 `wecom_id_binding_codes`（迁移 0055 · 6 位数字 / TTL 10 分钟 / 一次性 / 3 次每小时每用户）；ingest 入口由 `activateFromCallback` 扩为 `ingestCallback`（登记 + 码匹配 + 会话内回执）。
- ingest 条件：chattype=single 且 cmd=aibot_msg_callback 且 fromUserId 非空 → upsert（幂等）；**enter_chat 等事件不激活**；未匹配用户 → 掩码 warn 忽略（同群先例）。
- 发送成功可旁证回填激活态（D4 · 默认做；来源标记随实现段）。

### 3.3 发送面（aibot 单聊）

- `WecomAibotClient` 增 `sendUserMarkdown`（或按 chat_type 参数化）：body = {chatid: userid, chat_type: 1, msgtype: markdown, markdown: {content}}；复用订阅态检查 / req_id / ack / 掩码口径；**帧形先复核官方语义 + stub 锁帧（P4）**。
- 限速：`WecomRateKind` 增 `single`；桶键 = `single:` + userid 摘要（镜像 group 桶键口径）；窗口先复用 `WECOM_BOT_RATE_LIMIT_PER_MINUTE / HOUR`（双窗口），单聊实测后决定是否拆独立 env（P5）。
- 本地限速拒绝 → deferred（不消耗重试，窗口翻转自动送达 —— 同群口径）。
- **绑定码口径修订（v1.13 · 2026-10-16 · Push 247）**：`chatid` 填的值不再取 `users.username`，改读**绑定行的 `wecom_userid`（密文 open_userid）**，且一律带 `bot_id = WECOM_BOT_ID` 条件；无绑定行 → 不发帧（dead + D4 绑定指引降级）。帧形（P4）与 `sendUserMarkdown` 出参不变；新增 `replyToCallback`（会话内回执 · `aibot_respond_msg` + 回调 `req_id` 透传）。

### 3.4 消费器 `NotifyDmService`

- 骨架对照 `NotifyAppService` / `NotifyGroupService`：解析载荷 → 读收件人 → **读绑定行（寻址地址 + 是否可投递）** → markdown 组装（加粗标题 + 空行 + 正文）+ 20000 字节截断（同群口径）→ 限速 → 发送 → 三分类收敛 + `notify_deliveries`（channel = 新值、target = userid）留痕。
- 失败收敛：rate_limited → deferred；retryable → retry；permanent（含 846607 未激活）→ dead + C5-04 同人站内信降级（**前缀附绑定指引话术 —— D4 终稿 2026-10-16：「当前用户未绑定企业微信，请前往设置补绑」（常量 `DM_BINDING_DEGRADE_PREFIX`，取代原 P3 激活指引话术）**；幂等 `:c504`）。
- 收件人**未绑定企微（无绑定行）** → 不发帧，dead + D4 绑定指引降级；收件人不存在 / 停用 / 离职 → dead，不降级（同 app 口径；用户存在即降级）。
- aibot 未订阅（连接态不可用）→ 按 retry 收敛（不误报成功、不丢事件）。
- 注册表门控（接线段定案 · 2026-10-14）：`notify.message` 的 `wecom_aibot` 分支**不按凭据门控注册**（区别于群通道「未配置 = 只存不投」）—— 未配置 / 未订阅时消费按 retry 收敛（bounded by outbox 重试上限 → dead + 告警），保证投递结果如实留痕、不静默丢；排障态可用 `NOTIFY_DELIVERY_ENABLED=false`（整体只存不投）。差异理由：单聊发送依赖常驻长连接（可恢复态），且激活面与发送面解耦 —— 引导激活的回调 ingest 不依赖发送配置。
- 免打扰口径：与 M5-03-3 应用消息面保持一致（不做投递前 DND 过滤）；如需变更另开口径。

### 3.5 846607 分流口径（关键）

- 命中激活表 → rate_limited（deferred）；未命中 → permanent（按未激活收口 → dead + 降级）。
- 依据：本地限速已前置挡量，未命中 + 846607 以未激活解释为主；不引入无限延期重排。
- 残余边界（激活早于上线 / 表滞后）依靠 D4 旁证回填 + 真机补测（P6）收敛，登记为已知边界。

### 3.6 保留自建应用（备用通道）

- `NotifyAppService` / `WecomClient` / app 码表 / env / 路由分支全保留；规则不再产出 `wecom_app` 后自然闲置。
- 回退（D6）= 4 条规则渠道值回切 `wecom_app`；文档标注「备用通道（未启用）」。
