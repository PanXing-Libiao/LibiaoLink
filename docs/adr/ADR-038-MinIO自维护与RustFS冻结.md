# ADR-038 对象存储：MinIO 自维护，RustFS POC 冻结

- 状态：已采纳（Accepted · 2026-10-26 用户定调，随本 PR 合并 main）｜评审：wmj、lan、px
- 日期：2026-10-26｜决策人：用户（2026-10-26 定调）
- 依据：ADR-006、ADR-013、`deploy/minio/README.md`、`deploy/prod/minio/MAINTENANCE.md`、RustFS 1.0.3 POC 记录
- 实施责任：lan（平台 / 构建 / S3 兼容性）、px（部署 / 备份 / 监控）、wmj（ADR / 契约 / 安全复核）

## 背景

文件是本项目最重的一类资产：图纸与三维文件常见几百 MB，需要预签名直传、分片与断点续传、版本控制、生命周期与异地备份；同时「不允许上传第三方云」是业务硬约束。ADR-006 已定案接口层只依赖 S3 协议、实现可替换，但当时因 MinIO 上游归档、官方二进制分发下线，没有把 MinIO 锁定为生产实现。

2026-10-26 完成 RustFS 1.0.3 隔离 POC 与同机同负载 A/B：功能回放均为 24 / 24，但 RustFS 的版本删除明显慢于 MinIO，100 个版本约 25.0 s、435 个版本约 2 min；MinIO 分别约 0.18 s、2.55 s。两轮结果一致，版本清理约 138 倍差距。源码检查指向本地磁盘执行层对对象 / 版本组的串行删除（`crates/ecstore/src/disk/local.rs`），不是单个配置项；上游已有 1.0.4，但尚未按同一负载复测。

| 指标（同机同盘单次工程 A/B） | MinIO | RustFS 1.0.3 |
|---|---:|---:|
| 功能回放 | 24 / 24 | 24 / 24 |
| 100 版本清理 | 约 0.18 s | 约 25.0 s |
| 435 版本清理 | 约 2.55 s | 约 2 min |
| 64 MiB 分片上传 | 15.6 MiB/s | 13.7 MiB/s |
| 64 MiB GET | 73.6 MiB/s | 103.5 MiB/s |
| 磁盘放大 | +0.064% | +0.071% |

以上为同一测试机、ext4、同一 AWS SDK、每容器 1 vCPU 的单次工程对比，不是 SLA 认证。

## 决策

1. **生产实现改为自维护 MinIO**：沿用已锁定的 `RELEASE.2025-09-07T16-13-09Z`（commit `07c3a429bfed433e49018cb0f78a52145d4bedeb`）作为基线，生产使用本地构建镜像，不再依赖 quay / Docker Hub / dl.min.io 等上游分发渠道。
2. **维护范围限定为最小下游补丁**：只接受安全漏洞、基础镜像 / 运行时依赖、关键 S3 正确性修复；不做功能分叉，不把 MinIO 特有 API 带入业务代码，不把存储内核并入 LibiaoLink 主仓的普通业务开发。
3. **补丁最小化**：无安全或正确性需求时保留已验证的官方静态二进制；需要修改时从锁定源码 commit 构建，补丁单独留档，镜像名为 `libiaolink/minio:<基线版本>-p<序号>`，并记录补丁 ID、源码 commit、构建时间、镜像 digest 与 SBOM / 哈希。
4. **固定验收门禁**：每次重建或升级必须通过 `npm run storage:init -- --check`、`npm run storage:it`（24 / 24）、分片上传、预签名 PUT / GET、版本删除、CORS、匿名拒绝、对象锁 / 版本语义与备份恢复抽检；关键指标相对基线出现无法解释的明显退化时阻断发布。
5. **职责固定**：lan 负责源码 / 构建 / S3 兼容性与补丁评审，px 负责部署、密钥边界、备份、监控与回滚演练，wmj 负责 ADR、契约和安全复核。没有指定负责人和回归证据的 MinIO 变更不得进入生产。
6. **RustFS 冻结**：RustFS 保留为 POC，不 fork、不改源码、不接 `api` / `worker`、不迁移对象、不进入生产；测试机 POC 可在确认后停止并保留证据。后续只有在上游修复版本删除瓶颈、通过同一 A/B 与 `storage:it` 后，才重新评估。
7. **接口层不变**：继续只依赖 S3 协议；MinIO 仅经内网 / 同源门面提供，不直接对公网开放。未来迁往公司内网 S3、SeaweedFS 或其它兼容实现时，不改业务调用代码。

## 备选与不采用原因

- **Fork / 自研改造 RustFS**：Apache-2.0 允许修改，但版本删除瓶颈位于存储执行核心，修复需处理锁顺序、崩溃恢复、命名空间事务和逐键错误语义；三人团队长期维护成本过高，且当前没有必须 fork 的业务收益。
- **继续使用归档 MinIO、不做自维护**：上游归档、官方分发下线，安全更新无人负责；一旦出现 CVE 或关键缺陷，生产将无补丁路径，因此不采用。
- **立即迁移 SeaweedFS**：仍需新存储验证、迁移和运维切换；当前 S3 抽象已保留替换能力，先以 MinIO 自维护降低迁移风险。
- **公司内网既有 S3 / 商业对象存储**：若后续确认可用且满足数据不出内网约束，可重新评估；当前没有可落地的既有服务结论。

## 影响与后果

- 正面：不迁移现有对象；沿用已验证的 S3 行为、版本语义和运维脚本；RustFS 的性能风险不进入生产。
- 负面：团队正式接管 MinIO 的安全更新、构建、CVE 跟踪和回归；上游没有官方支持，所有补丁责任在本地。
- 约束：只做最小补丁；每次升级必须有备份、上一版镜像与回滚方案；不能把「能启动」当作验收完成。
- 许可：MinIO 为 AGPL-3.0。内部自用通常不是阻塞，但修改后向用户提供网络服务、对外分发镜像或交付客户时的源码提供义务，必须由法务确认；保留 LICENSE / NOTICE 与对应源码。

## 切换触发条件

- MinIO 源码无法在受支持工具链构建，或关键 CVE 无法在可接受时限内修复。
- `storage:it`、版本删除、分片、预签名或对象锁出现不可接受的回归，且下游补丁无法修复。
- 容量、可用性、合规或数据不出内网要求变化，现有单机 MinIO 形态不再满足。
- 公司内网出现有支持的 S3 服务，或 SeaweedFS 等替代实现通过同一验收矩阵。
- RustFS 上游修复版本删除瓶颈并通过同一 A/B 与完整 `storage:it`，可重新评估，但不自动改变本决策。
