# MinIO 自维护清单（生产）

- 依据：ADR-038
- 适用：`deploy/prod` 的 MinIO 生产 / 测试机生产形态；本地沙箱仍见 `deploy/minio/README.md`
- 当前基线：`RELEASE.2025-09-07T16-13-09Z`，commit `07c3a429bfed433e49018cb0f78a52145d4bedeb`，官方静态二进制 SHA-256 `7c5bd8512c6e966455b1d198209358b2d191c77a83ab377c4073281065fb855f`
- 基础镜像：`alpine:3.24@sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6`（当前 Dockerfile 固定值）
- 责任：lan（源码 / 构建 / S3 兼容性）、px（部署 / 备份 / 监控 / 回滚）、wmj（ADR / 契约 / 安全复核）

## 1. 维护边界

允许：

- 安全漏洞、基础镜像 / 运行时依赖更新；
- 关键 S3 正确性修复（版本删除、分片、预签名、对象锁、错误语义）；
- 为可复现构建所需的构建脚本、SBOM 与镜像标签调整。

禁止：

- 功能分叉、UI / 控制台改造、业务专属逻辑；
- 在 `api` / `worker` 中依赖 MinIO 特有 API；
- 未经评审的数据库 / 对象键 / 桶策略变更；
- 直接把 MinIO 源码整包并入 LibiaoLink 业务目录。

## 2. 版本与构建

- 内部保留基线源码快照、官方二进制、LICENSE / NOTICE、SHA-256 与构建记录；不得只依赖 GitHub Release 或 quay 可用性。
- 无补丁需求时，生产继续使用已验证的本地镜像；需要安全 / 正确性补丁时，从锁定源码 commit 构建。
- 构建必须固定 Go 工具链、基础镜像 digest 与依赖锁；产物记录：源码 commit、补丁 ID、镜像 digest、构建时间、构建人、SBOM / 哈希。
- 镜像命名：`libiaolink/minio:<基线版本>-p<序号>`；未打补丁的基线沿用 `libiaolink/minio:<基线版本>`。
- 构建产物先进入内部 registry 或受控离线目录，禁止从来源不明的第三方镜像站拉取。

## 3. 补丁流程

1. 建立补丁记录：CVE / issue 编号、影响范围、上游参考、最小 diff、回滚方式。
2. 在独立分支完成补丁，保留原始源码与 diff；不得夹带功能改动。
3. 本地构建并跑第 5 节回归矩阵；记录实际命令、版本、digest 与结果。
4. 由 lan 做源码 / 兼容性复核，wmj 做安全复核；px 确认部署与回滚路径。
5. 先在测试机生产形态验证，再进入生产维护窗口；未通过不得以「只改了一点」为由跳过。

## 4. 升级 / 发布检查单

- [ ] 已确认变更类型属于安全 / 依赖 / 关键正确性，不含功能分叉。
- [ ] 已记录当前版本、目标版本、源码 commit、补丁 ID、镜像 digest 与 SHA-256。
- [ ] 已备份 PostgreSQL 与 MinIO 数据目录 / 对象清单，并登记备份位置、大小、校验值。
- [ ] 已保留上一版镜像 digest 与可回滚数据快照。
- [ ] 已确认新版本对现有数据格式的兼容性；不支持就地降级时，明确「以备份恢复代替二进制回退」。
- [ ] 测试机生产形态通过第 5 节全部回归项。
- [ ] 生产窗口内只重建 `minio`，不重启 `api` / `worker` / `web`（除非变更明确要求）。
- [ ] 升级后 `/healthz` / `/readyz`、`storage:init --check`、`storage:it`、同源门面预签名 PUT / GET 均通过。
- [ ] 记录升级结果、耗时、异常、证据路径与后续事项。

## 5. 回归矩阵

每次重建 / 升级至少执行：

- `npm run storage:init -- --check`；
- `npm run storage:it`（24 / 24）；
- 分片上传（至少 64 MiB，8 MiB part）与中断后续传；
- 预签名 PUT / GET / DELETE 与真实浏览器 CORS；
- 版本控制、删除标记、定档对象不可变；
- 对象锁 / 保留策略（如启用）；
- 匿名对象 GET 拒绝、非法 Origin 不回 ACAO；
- 未完成分片清理与草稿 30 天应用侧清理；
- 同机同负载版本清理基准（100 个版本；必要时 435 个版本）。

判定：功能断言必须全绿；关键指标相对基线出现无法解释的退化先排查，超过基线 2 倍或影响业务 SLA 时阻断发布。基准是工程对比，不是对外 SLA。

## 6. 备份、恢复与回滚

- 备份必须同时覆盖数据库与对象数据；只备份 PostgreSQL 不等于文件可恢复。
- 至少每季度做一次「数据库 + 文件」恢复演练，抽检「项目 → 任务 → 附件 → 版本 → 哈希」链路。
- 升级前保留上一版镜像 digest 与数据快照；回滚前先确认旧版本能读取新版本写入的数据。
- 不支持就地降级时，停止写入、恢复数据快照、切回上一版镜像，再执行 `storage:init --check` 与 `storage:it`。
- 备份、工单、聊天和日志中不得出现 root / service account 明文；Secret 继续走 `_FILE` 与 600 权限。

## 7. CVE 与维护节奏

- 每月检查 Go 依赖、基础镜像、MinIO 安全公告与仓库 issue；记录结论，不把「未扫描到」写成「无风险」。
- 严重 / 高危 CVE：24 小时内评估，目标 7 天内完成补丁或书面风险接受；其余按月度窗口处理。
- 即使没有新 CVE，也建议每季度重建一次基础镜像并跑完整回归；重建不等同升级，仍需备份与回滚。
- 上游归档不代表可以忽略依赖树；MinIO 自身与基础镜像的漏洞都要纳入跟踪。

## 8. 许可与分发

- MinIO 为 AGPL-3.0；保留 LICENSE / NOTICE 与对应源码，修改版本必须标注修改。
- 内部自用通常不是阻塞；向用户提供网络服务、对外分发镜像或交付客户前，必须由法务确认源码提供与通知义务。
- 不把 MinIO 镜像或源码用于暗示官方支持 / 背书。
